## B. Проблеми/прогалини джерел (НЕ слід приховувати в дипломі)

1. **AHP vs sliders:** у §1.3 — попарні порівняння за шкалою Сааті; на А.4 — прямі слайдери пріоритетів. Потрібно два режими (AHP та WSM) і окрема чесна термінологія.
2. **База даних vs scheduling:** макети А.6, А.8 згадують запис/розклад; описані 16 таблиць не мають слотів/записів. MVP додає тільки заявку на консультацію.
3. **AHP матриця vs storage:** таблиця `criterion_priorities` має ваги, але не повні raw pairwise judgments; MVP додає `CriterionComparison`.
4. **Radius vs location:** `search_requests.radius_km` є, але координат у вихідній `specialists` немає. Реальна дистанція не може бути обчислена; використовувати обрані місто/район як дискретну soft-оцінку.
5. **Рейтинг:** таблиця `reviews` і поле `specialists.rating` є, але політика обчислення/модерації не формалізована; для MVP із APPROVED review only.
6. **Логіка IDEF0 A1:** у звіті блок названо «Авторизація», а пояснення описує введення параметрів пошуку. У робочому коді це два окремі процеси.
7. **Надмірне формулювання «розроблена система» в минулому звіті:** звіт описує концептуальну систему, а не містить доведену працездатну реалізацію. Не видавати вихідну роботу за вже готовий код.
8. **Продуктивність**: якісні NFR є, але виміряні контрольні часи в джерелах відсутні; числа у PRD — нові критерії, їх треба перевірити.

## C. Рішення MVP, які НЕ є прямими вимогами DOCX

- React+Vite+TypeScript, Tailwind, Prisma, Docker Compose, сесії/тести/API контракти — engineering design choices.
- Guest access до каталогу, але рекомендації із збереженням історії тільки для patient session — практичний UX компроміс.
- Hybrid AHP-derived criteria weights + WSM alternative scores. Це чесно позначена методична адаптація для великої кількості альтернатив; **не повний AHP за всіма альтернативами**.
- Fixed normalization ranges: EXPERIENCE 0–20 років, PRICE 300–3000 UAH, RATING 1–5, LOCATION nominal city/district, FORMAT match. Ці константи треба обґрунтувати як експериментальні у магістерській роботі після тестування.
- Пряма WSM альтернатива як baseline для дослідження.
- Синтетичний seed, демонстраційна роль і дисклеймер замість реального каталогу лікарів.
- Мінімальні запити на консультацію замість реального calendar-slot booking.
- Відсутність зовнішніх API, OAuth, payments, notification infrastructure, ML, real medical records.

## D. Рішення власника, які залишено для post-MVP

- чи потрібна повна перевірка кваліфікації фахівця;
- чи відкривати сервіс реальним користувачам;
- чи потрібен реальний календар/оплати/онлайн-консультації;
- чи треба переробити наукові діаграми відповідно до фактичної гібридної математичної моделі.

Cursor НЕ повинен блокувати локальний MVP через ці post-MVP питання.

## E. Авторитет у разі розбіжностей

- **Наукові твердження:** оригінальні звіти, без самочинного переписування.
- **Поведінка локального MVP:** документи цього пакета з позначками engineering decisions.
- **Візуальний стиль:** оригінальні PNG з додатка А, а токени лише approximate.
- Будь-яке рішення, яке змінює scope/формули/повноваження ролей — документувати до реалізації та запитати власника, якщо впливає на достовірність MVP.
