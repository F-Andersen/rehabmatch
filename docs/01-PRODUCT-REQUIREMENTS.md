# 01. Технічне завдання / PRD для MVP RehabMatch

## 1. Контекст та ціль

Система підтримки прийняття рішень для **інтелектуального підбору спеціалістів з реабілітації на основі аналізу потреб пацієнта**. Основа — індивідуальний багатокритеріальний аналіз (AHP/МАІ з вагами критеріїв; нормалізоване зважене оцінювання альтернатив). Назва проєкту та макетів: **RehabMatch**.

Джерела: «Звіт з переддипломної практики» (особливо §2.2, §2.3, §3.1–3.3) і «Диплом1» (додаток А, зокрема п. 2.1–2.3, рис. А.1–А.8). Розходження вирішені у `10-SOURCE-MAPPING-AND-DECISIONS.md`. Не ототожнювати рекомендаційну оцінку із клінічною ефективністю фахівця.

## 2. Ролі

**Patient**: реєстрація/вхід, профіль, пошук/фільтрація, введення пріоритетів, перегляд/збереження рекомендацій, відгуки, заявки на консультацію. **Specialist**: реєстрація/вхід, редагування власної анкети, спеціалізацій, досвіду, типів травм, формату, вартості та послуг, перегляд і прийняття/відхилення заявок. **Admin**: модерація та підтвердження спеціалістів, користувачі, довідники, критерії, відгуки, заявки, мінімальний огляд стану системи. Пацієнт не може призначити собі іншу роль через API.

## 3. MVP scope — включено

**MVP-F01 (Auth)**. Email/password, хешування пароля, сесії HTTP-only cookie, login/logout, role-based guards. Початковий admin створюється лише seed-скриптом через секрети з env (не публікувати паролі). Google/Facebook OAuth відкладено; кнопки OAuth не повинні вводити в оману.

**MVP-F02 (Profiles)**. Пацієнт має мінімальний профіль (ПІБ опційно, місто); чутливі медичні дані не збирати. Спеціаліст редагує профіль: ім'я, демо-фото або ініціали, місто/район, досвід, опис, ціна, спеціалізації, релевантні запити/травми, доступні формати, інклюзивність, послуги. Новий профіль не відображається публічно, доки admin не встановить APPROVED. Усі seed-профілі позначені demo.

**MVP-F03 (Catalog)**. Список спеціалістів, текстовий пошук за ім'ям/спеціалізацією, фільтри за injury type, specialization, city, district, priceMax, format, inclusiveSpace; сортування за рейтингом, ціною, досвідом, новизною; серверна пагінація. Гостьовий перегляд каталогу дозволений, щоб полегшити демонстрацію. Для збереження запитів потрібен вхід як patient.

**MVP-F04 (Preferences)**. Вибір п'яти критеріїв: досвід, вартість, рейтинг/відгуки, локація, формат. Режим `AHP_PAIRWISE` — попарні оцінки шкалою Сааті 1…9 (або обернені), показ ваг та CR, блокувати результат при CR>0.10 і показувати, що потрібно переглянути. Режим `DIRECT_WSM` — інтерактивні вагові повзунки 1–9, нормалізація до 100%; цей режим **не є AHP**. UI за А.4: п'ять рядків та підсумкові відсотки; для AHP рядки відображають ваги як read-only, а ввід у wizard.

**MVP-F05 (Recommendations)**. Ввід параметрів запиту → hard filters → критерії → валідація → обчислення ваг → scoring і ранжування → пояснення для кожного кандидата → запис у БД → перегляд історії пацієнта. Зберігати алгоритм, версію, weights, snapshot scored factors, CR, дату. Виводити нормалізоване число `0.000–1.000` як «показник відповідності вашим пріоритетам», не «точність лікування». При однакових результатах використовувати детерміноване сортування.

**MVP-F06 (Profiles & reviews)**. Детальна сторінка спеціаліста: профіль, вартість, послуги, відгуки, опис. Відгук — лише зареєстрований patient, одна активна оцінка одного спеціаліста від користувача (можна редагувати), rating 1–5, модерація admin до публікації. Публічний рейтинг тільки зі схвалених відгуків; якщо відгуків немає — «немає оцінок», а не «5.0».

**MVP-F07 (Appointment request)**. Пацієнт створює **запит** із бажаною датою/часом; specialist бачить запит, приймає або відхиляє; patient може скасувати до прийняття; admin може переглядати й модерувати. Це **не бронювання реального слоту**, не підтверджений запис у клініку, без зв'язку з реальним календарем. Не дозволяти вибір дати в минулому. Статуси REQUESTED, ACCEPTED, DECLINED, CANCELLED; для UI текст «Надіслати запит на консультацію».

**MVP-F08 (Admin)**. Dashboard з таблицею users, specialist verification queue, каталогом довідників, критеріями, reviews moderation, заявками. Backend перевіряє admin роль у кожному привілейованому API. Адмін не може випадково відкрити password hashes у відповідях API.

**MVP-F09 (Responsive/accessible)**. Макети А.1–А.7 як desktop reference, мобільні 375–430px + tablet. Дієві меню, focus states, підписи, keyboard-friendly форми, контрасти, пояснення помилок і порожні стани.

## 4. Поза обсягом MVP

Онлайн-оплата; повне календарне бронювання з управлінням ресурсами; реальна інтеграція з лікарнями/eHealth/Helsi; телемедицина; відеозв'язок; медичні картки; діагностика; нейромережі, Ollama чи генеративний AI; external OAuth; підтвердження чинності професійної ліцензії; масове імпортування реальних лікарів; геокодування/маршрути; email/SMS push; мультимовність (після MVP); деплой у public production. Якщо агент пропонує ці функції — винести у backlog, не роздувати MVP.

## 5. Бізнес-правила

- Операції вибору фахівця, які впливають на рейтинг, мають враховувати лише APPROVED спеціалістів. Сервер не довіряє прапорцям `verified`, `rating`, `role` із клієнта.
- Обов'язкові фільтри: обраний тип травми/категорія компетенції, прийнятний бюджет, доступний формат; місце стає hard-фільтром тільки якщо користувач явно встановив «лише в моєму місті». Інакше location бере участь у scoring.
- Відсутність кандидата: показати «За заданими умовами нікого не знайдено» та можливість пом'якшити лише необов'язкові обмеження, **не імітувати результат**.
- Відсутні поля не призводять до `NaN`. За відсутності rating робити нейтральну оцінку для рейтингового критерію та помітку «недостатньо відгуків»; дані ніколи не підмінювати вигаданими цифрами.
- Ціни — UAH per session, точне число з PostgreSQL Decimal. Демо-значення не є реальними ринковими офертами.
- Пацієнт може переглядати тільки свої збережені пошукові запити, рекомендації та заявки. Спеціаліст — тільки адресовані йому заявки.
- Для статусів відгуків: PENDING/APPROVED/REJECTED. Об'єктивної перевірки факту відвідування в MVP немає; не маркувати «відгук після візиту».
- Заявка на консультацію може бути ACCEPTED, але це підтвердження спеціалістом у демосистемі, не фактичний медичний запис.

## 6. Основні сценарії користувачів (acceptance)

**SC-01** Patient реєструється і входить, після перезавантаження сесія залишається чинною, logout припиняє її.
**SC-02** Specialist створює анкету; до підтвердження адміністратора в публічному каталозі її немає; після APPROVED з'являється.
**SC-03** Guest переглядає каталог, міняє фільтри, бачить коректні результати, може відкрити профіль.
**SC-04** Patient вводить сценарій і AHP порівняння; якщо CR>0.1 — отримує зрозумілу помилку та спосіб виправлення; якщо CR≤0.1 — може отримати рейтинг.
**SC-05** За однакових кандидатів і різних ваг рейтинг змінюється; причини змін показуються у breakdown.
**SC-06** У WSM quick mode користувач змінює слайдери, сума ваг стає 100% і mode зберігається як DIRECT_WSM.
**SC-07** Patient залишає відгук; до схвалення admin він не впливає на публічний рейтинг.
**SC-08** Patient створює заявку; specialist змінює статус; обидва бачать фактичний стан із БД.
**SC-09** Гостьові спроби POST до приватних API повертають 401, чужі об'єкти — 403/404, не змінюють БД.
**SC-10** Повний локальний запуск з чистого стану документований у README, міграції та seed завершуються успішно.

## 7. Нефункціональні вимоги / запропоновані цільові показники MVP

З оригінальних звітів: продуктивність, масштабованість, захист даних, зрозумілість, пояснюваність. Числові орієнтири нижче — **нові критерії приймання MVP**, а не числа з DOCX: локально на 500 синтетичних профілях p95 GET /specialists < 500 мс і POST /recommendations < 1500 мс без мережевих затримок (на типовому сучасному ноутбуці, описати конфігурацію); відсутність очевидних критичних помилок тестів; адаптивний UI 375px/768px/1440px; детермінований алгоритм з відтворюваними метриками.
